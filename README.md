# Task Service

Сервис для управления задачами с HTTP API на Go.

## Требования

- Go `1.23+`
- Docker и Docker Compose

## Быстрый запуск через Docker Compose

```bash
docker compose up --build
```

После запуска сервис будет доступен по адресу `http://localhost:8080`.

Если `postgres` уже запускался ранее со старой схемой, пересоздай volume:

```bash
docker compose down -v
docker compose up --build
```

Причина в том, что SQL-файл из `migrations/0001_create_tasks.up.sql` монтируется в `docker-entrypoint-initdb.d` и применяется только при инициализации пустого data volume.

## API

Базовый префикс API:

```text
/api/v1
```

Основные маршруты:

- `POST /api/v1/tasks`
- `GET /api/v1/tasks`
- `GET /api/v1/tasks/{id}`
- `PUT /api/v1/tasks/{id}`
- `DELETE /api/v1/tasks/{id}`

## Повторяющиеся задачи

При создании задачи можно передать поля:

- `recurrence_type`: `daily`, `monthly`, `dates`, `even_odd`
- `recurrence_config`: JSON-конфиг для выбранного типа

Если у задачи задана периодичность, она сохраняется как шаблон, а фоновый воркер
периодически создаёт экземпляры задач и сдвигает `next_run_date`.

## Что реализовано по тестовому заданию

- Добавлены настройки периодичности: `daily`, `monthly`, `dates`, `even_odd`.
- Реализована валидация `recurrence_type` и `recurrence_config` при создании.
- Периодическая задача сохраняется как шаблон (запись с `parent_task_id = NULL`).
- Фоновый воркер создаёт экземпляры задач из шаблонов по `next_run_date`.
- После создания экземпляра воркер пересчитывает следующую дату запуска шаблона.
- Добавлен фильтр в `GET /api/v1/tasks?filter=`:
	- `all` (по умолчанию),
	- `templates`,
	- `instances`.

## Принятые допущения

- Шаблон задачи хранится в той же таблице `tasks`.
- Экземпляр задачи - отдельная запись со ссылкой `parent_task_id` на шаблон.
- Для `monthly` допустимы дни месяца от `1` до `30` (согласно формулировке задания).
- Для `dates` при отсутствии будущих дат новые экземпляры больше не создаются.
- Время расчётов и запусков - `UTC`.

## Примеры запросов

Создать ежедневный шаблон:

```json
{
	"title": "Ежедневный обзвон",
	"status": "new",
	"recurrence_type": "daily",
	"recurrence_config": {
		"interval_days": 1
	}
}
```

Получить только шаблоны:

```text
GET /api/v1/tasks?filter=templates
```

Получить только экземпляры:

```text
GET /api/v1/tasks?filter=instances
```

## Отчет по выполнению тестового задания

### Цель

Реализовать периодические задачи в существующем API трекера задач без ломки текущего CRUD и с понятным поведением в граничных сценариях.

### Что было сделано

- Добавлены типы периодичности: `daily`, `monthly`, `dates`, `even_odd`.
- Добавлены поля `recurrence_type`, `recurrence_config`, `next_run_date`.
- Реализована модель шаблона и экземпляров:
	- шаблон: запись с `parent_task_id = NULL`;
	- экземпляр: запись со ссылкой `parent_task_id` на шаблон.
- Запущен фоновый воркер (каждые 30 секунд), который:
	- ищет шаблоны с `next_run_date <= now`;
	- создает экземпляры задач;
	- пересчитывает следующий запуск шаблона.
- Добавлен фильтр списка: `all`, `templates`, `instances`.

### Что в ТЗ было не до конца определено (и как это решено)

1. Как хранить периодичность и связь между исходной задачей и копиями.
Решение: одна таблица `tasks`, связь через `parent_task_id`. Это уменьшает сложность и не требует отдельного API для шаблонов.

2. Когда именно должна появляться копия задачи.
Решение: периодический воркер. Копия создается при наступлении условия `next_run_date <= now`.

3. Поведение ежемесячных задач в месяцах с разным числом дней.
Решение: по ТЗ поддержаны дни `1..30`; если целевой день больше доступного в месяце, берется последний доступный день.

4. Поведение для `dates`, если будущих дат больше нет.
Решение: новые экземпляры больше не создаются, `next_run_date` становится `NULL`.

5. Временная зона вычислений.
Решение: все расчеты и сравнения выполняются в `UTC` для предсказуемости.

6. Глубина валидации `recurrence_config`.
Решение: строгая валидация входа:
	- `recurrence_config` без `recurrence_type` запрещен;
	- для периодической задачи `recurrence_config` обязателен;
	- JSON должен быть валидным;
	- тип периодичности нормализуется и проверяется.

### Как проверялось

- Swagger: ручной прогон позитивных и негативных сценариев.
- Unit-тесты: расчеты `next_run_date`, граничные условия по типам периодичности, валидация create/list.

### Итог

Функциональность периодических задач добавлена в существующий сервис, покрывает основные пользовательские сценарии и учитывает ключевые неявности ТЗ с явными допущениями.
